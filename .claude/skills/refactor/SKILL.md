# /refactor — Postmortem or implementation update

## What it does
Helps document why an already-made implementation is changing. There are two cases, and the first step is always to distinguish which one applies — not to assume it:

1. **Postmortem (something went wrong).** The human explains what failed, and this skill helps structure it by asking the right questions — it doesn't guess the problem on its own. Output: a new postmortem ADR (`ADR-[feature]-postmortem.md`).
2. **Decision update (nothing went wrong, preference changed).** The human wants to change the pattern/approach without a bug having occurred — for example, switching from `useMemo` to `useState` because they prefer async values to be explicit state, not because `useMemo` failed. Output: a postmortem ADR is NOT created — an "Update" section is added to the original feature ADR (the one generated by `/model`), documenting the change, that it doesn't fix a bug, and the new reasoning.

**How to distinguish:** ask directly — "Does this fix a real problem you observed, or is it a preference change without anything being broken?" — before choosing the output format. Don't force a postmortem when nothing went wrong; forcing it produces a document that invents failures that didn't occur.

## Scope — what this does NOT cover
This command produces documentation only about the implementation (the code). It does not cover view, service interfaces, or the combination of both — those artifacts already have their own commands (`/view-implementation`, `/placeholder-implementation`, `/full-implementation`) with their own outputs.

## Example — postmortem (case 1)
```
# ADR-pokemon-search-postmortem

## What was planned
(summary of ADR-pokemon-search)

## What went wrong
- The 300ms debounce caused visual flickering in results
- Slow network / timeout case was not handled

## What was fixed
- Debounce increased to 400ms + loading state
- Timeout handling with retry
```

## Example — decision update, no bug (case 2)
Added directly to the original ADR, not to a new document:
```
## Update — promise lives in useState, not in useMemo
Does not fix a bug — useMemo was working correctly. It's a pattern
preference: model async state explicitly in useState instead of
deriving it with useMemo, so it's clear it's the source of truth
the child component reads via use().
```
